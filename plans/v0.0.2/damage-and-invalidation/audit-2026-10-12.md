# Departure board frame path audit (2026-10-12)

Read-only audit. No repo files were created, edited, or deleted. Evidence is
against `internal/window` and `internal/page` at HEAD `8cd5332` (the
`examples: add departure-board and theme-studio demos` commit) plus the
uncommitted `examples/departure-board/main.go` flag wiring. `internal/` is clean
at that commit, so the line numbers below are stable. The board-side citations
(`board/tick.go`, `board/flip.go`, `board/board.go`) describe the pre-F1
working tree as I read it during this audit; F1 started adding
`board/dirty.go`, `board/flip_bar.go`, and `board/flip_rebind.go` while I was
reading, so those three files may have moved by the time you read the ranked
list.

Two micro-measurements were run outside the repo, in `/tmp/opencode`, using
copies of the relevant logic. They are marked "measured" below. Everything else
is code reading; numbers I derived rather than measured are marked "estimate".

## Headline finding, confirmed

`internal/window/replay_frame.go:10-18` makes `fullReplay()` true when the screen
is ticking and does not answer `FrameDirty()`:

- `isTicking()` from `internal/window/replay_oversize.go:26-30` asks the screen
  for `Ticking() bool`. The window's screen here is `app.Page()` (`main.go:61`),
  a `*page.Page`, and `Page.Ticking()` is `p.tick != nil`
  (`internal/page/page_ticking.go:6-8`). `board.New` calls
  `p.SetTick(a.Tick)` (`board/board.go:42`), so `Ticking()` is true for the life
  of the board.
- `Page.FrameDirty()` (`internal/page/page_frame.go:15-20`) is only true after
  `UseFrameDirty()` (`page_frame.go:12`), which the board never calls. So
  `marker.FrameDirty()` is false and `fullReplay()` returns true every frame.
- `drawReplayPartial` (`internal/window/replay_partial.go:37-50`) takes the
  `!canTake || s.fullReplay() || !s.bufferOrderSafe()` branch (line 45),
  calls `disposeViewport()` (a nil-buffer no-op) and `directReplay` (line 47).
- `directReplay` (`replay_oversize.go:36-40`) calls
  `replay.DrawVisiblePinned`, which walks `display.Order` once and draws every
  op whose bounds meet the window rect (`internal/replay/visible.go:20-46`).
  For a board that fits the window, that is every op, about 1060 of them.

The board's tick mutates the display list in place. `flipper.step`
(`board/flip.go:82-102`) writes `fl.op.Text`, `tick.go:70` writes the clock text
and `tick.go:76` writes the refresh bar width. No `Redraw` runs during a tick
except the night flip (`tick.go:50-57`) and the 12 second `Advance`
(`data.go:62-71`). So the window has no dirty information and re-replays the
whole list every frame. This matches the reported 23 ms draw.

The dump harness's emulation in the spec (`p.Ticking() && !p.FrameDirty()` then
`TakeDirty`) reproduces this exactly: before F1 every frame classifies as
`full-replay` and `ReplayedOps` equals `Ops`.

## 1. What the window still does every frame on the buffer path

Once the page opts in (`UseFrameDirty` plus marks), `drawReplayPartial` keeps a
content-sized buffer and each frame does the following, in order.

`shell.Draw` (`internal/window/draw.go:9-36`):

| work | site | scales with |
| --- | --- | --- |
| `devFrameTime` (2 clock reads) | `draw.go:10`, `devtools_misc.go:11-18` | constant |
| `perfFrameSample` | `draw.go:11` | no-op unless Perf, see Q3 |
| `screen.Fill(pageBackground())` | `draw.go:13`, `background.go:12-31` | window pixel area |
| `pageBackground` scan | `background.go:35-70` | O(1) typically (first fill op wins), O(ops) worst case, 1 boxed-color alloc per call (measured) |
| `drawContent` -> `drawReplayPartial` | `draw.go:19-20`, `replay_partial.go:37-72` | op count and pixel area, below |
| `drawScrollbars` | `draw.go:21`, `scrollbar.go:38-57` | constant (2 `vector.FillRect` calls when shown, early return when not) |
| `drawMenu` | `draw.go:27-28`, `menu_draw.go:25-28` | constant (a bool check when closed) |
| `drawDevTools` | `draw.go:30-32` | none when closed, Q2 when open |

Inside `drawReplayPartial` (`replay_partial.go:37-72`) and `applyRepaint`
(`replay_buffer.go:12-35`):

- Type assertions and `contentSize()` (cached per generation,
  `content_size.go:10-33`) are constant. `bufferOrderSafe()` walks the order once
  per new display pointer and caches the answer (`replay_order.go:12-34`), so it
  is constant per frame after the first.
- `TakeDirty()` once per frame (`replay_partial.go:58`), O(1) (Q5).
- `planRepaint` (`replay_plan.go:32-52`) is O(1).
- `repaintBlit`: nothing. Zero op work, it just leaves the buffer alone.
- `repaintRect`: `SubImage` plus a `Fill` proportional to the rect area
  (`replay_buffer.go:27-29`), then `replay.DrawRectUnfixedZ`
  (`replay_buffer.go:31`), which walks the whole order and calls `opTouches` per
  op (`internal/replay/pinned_z.go:18-35`, `draw_rect.go:65-72`,
  `op_bounds.go:18-41`). So the walk is O(ops) with float math per op, and only
  the touching ops draw. Estimate 40-120 us per walk at 1060 ops on the
  reporter's machine.
- `repaintBuffer`: a full-content `Fill` plus `DrawUnfixedZ`, which draws every
  non-fixed op (`replay_buffer.go:14-21`, `pinned_z.go:10-16`). This is the
  expensive mode, roughly the old full replay plus a buffer fill.
- The blit `dst.DrawImage(s.partial.buf, ...)` (`replay_partial.go:67-69`): one
  image draw per frame, pixel area of the content, constant for a given size.
- `replay.DrawFixed` (`replay_partial.go:70`, `replay.go:50-65`): walks the whole
  order and draws only `op.Fixed` ops. The board has none, so this is a pure
  O(ops) filter walk, estimate 20-60 us.
- `replay.DrawPinnedZ` (`replay_partial.go:71`, `pinned_z.go:41-43` and
  `56-67`): walks the whole order, computes `opTouches` (which calls `opBounds`)
  for each op, and draws pinned ops. The board has none, so this is a second
  O(ops) walk with bounds math, estimate 30-100 us.

So on the buffer path, per-frame work that scales with op count is the two or
three filter walks (plus the actual op draws in the `rect` and `buffer` modes).
Work that scales with pixel area is the screen fill, the blit, and the buffer or
rect fill. Constant work is the scrollbars, the menu, `TakeDirty`, and the
asserts. Two things are worth calling out:

- The screen fill at `draw.go:13` is redundant whenever the blit will cover the
  screen, which it does when the content is at least as large as the window
  (the normal case, including fullscreen, because a resize commits the page to
  the window size at `resize.go:15-45`).
- The blit means the page always costs one full-content texture copy per frame,
  even on a `repaintBlit` frame. That is the floor once the buffer path is in
  use. It is far below 1060 draw ops, but it is not zero.

## 2. The devtools dock

Closed:

- `devSync` (`devtools_sync.go:5-24`) runs once per `Update`. It type-asserts
  `host.Inspector`, calls `Page.DevTools()` which returns a bool, and returns.
  Constant.
- `devRefresh` (`devtools_life.go:11-15`) returns before reading stats because
  `s.dev.on` is false. Constant.
- `Draw` skips `drawDevTools` entirely (`draw.go:30-32`).

So the closed dock costs a type assertion and a bool per frame. Nothing to fix.

Open, common per frame:

- `devRefresh` (`devtools_life.go:11-39`): sends the draw time to the page,
  copies `host.Stats` (about 150 bytes, includes a string) at line 21, and only
  on a generation change scans the box list for the hovered and pinned boxes
  (`devHasBox`, lines 32-38, `57-72`). The generation does not change during a
  flap, so that scan runs once per Redraw.
- `devLayout` (`devtools_layout.go:16-28`): places the dock, calls
  `devTabRows` (the per-tab work below), `devClampScroll` (O(1)), and `devHits`.
- `devHits` (`devtools_layout.go:33-61`): measures 3 tab labels and appends one
  `devHit` per visible actionable row. On the Ops tab that is one hit per op row
  (about 1060 entries, 64 bytes each, estimate 68 KB) into a slice reused across
  frames via `s.dev.hits[:0]`. The append loop itself is O(ops) with a measure
  call per tab label only.
- `drawDevPanel` (`devtools_panel.go:11-25`): 2 fills, header (1 measure, 1
  text draw), tab strip (3 measures, 3 text draws, 2 fills,
  `devtools_tabs_draw.go:10-34`), content, scrollbar, footer (1 measure, 1 draw).
  The content draw is bounded by the visible rows: `drawDevContent`
  (`devtools_content.go:36-54`) walks all rows but only draws rows inside the
  content rect, about 60 at 1080 px tall and 78 at 1440 (line height about 16 px,
  estimate). Each visible row does a SubImage clip per frame (line 42) and one
  text draw per span plus one measure per span (`devtools_row_draw.go:26-40`).
  The dock's drawing cost is therefore roughly constant in op count and grows
  slowly with window height, not with the number of ops.

Per tab:

- Elements (`devtools_element.go:10-31`). With no box picked it returns 4 static
  rows and costs almost nothing. With a hover or pin it rebuilds the payload
  every frame: `devElementPayload` (lines 47-63) calls `devOpsInBox`, which scans
  all 1060 ops and calls `devOpRect` -> `replay.PaintBounds` for each text op
  (`devtools_counts.go:47-63`, `devtools_oprect.go:15-29`), then
  `devJSONRows` (`devtools_json.go:11-16`) walks the struct with reflection and
  marshals scalars with `json.Marshal` (`devtools_json_value.go:10-17`), building
  a `*devJSONNode` per member and about 20 rows. So yes, the Elements tab
  rebuilds its JSON every frame, and its cost scales with the op count while a
  box is picked. Estimate 0.2 to 0.6 ms and a few KB per frame, plus 1060
  `PaintBounds` calls, all of it uncached.
- Frame (`devtools_frame.go:11-55`). Rebuilds roughly 45 to 50 rows per frame.
  Each right-aligned row measures three strings and builds a pad string with
  `strings.Repeat` (`devtools_frame_mem.go:12-18`), so about 150 `text.Measure`
  calls plus 2 `fmt` calls per row. The perf, pipeline, and memory sections read
  cached values through the window hooks (`devtools_frame_perf.go:16-59`,
  `perf_opt.go:35-59`); the runtime numbers come from the 500 ms sampler, not
  per frame. It also calls `ebiten.ActualFPS` and `ActualTPS` (lines 27-28).
  Estimate 0.15 to 0.4 ms and 2 to 5 KB per frame. This is the cheapest tab and
  the one whose numbers the user reads, so it flatters the frame a little.
- Ops (`devtools_ops_lines.go:13-70`). Two separate costs. It rebuilds the whole
  row list every frame: one row per painted op (about 1060), each with a
  `#n` string, a kind label, and a `fmt.Sprintf(" x%g y%g %gx%g")` (lines 53-55),
  a `devSpan` slice per row, and for text ops a `[]rune` conversion to truncate
  the label at 40 runes (lines 57-62, the `len([]rune(t))` allocates a rune slice
  per text op per frame). Estimate 0.5 to 1.5 ms, 200 to 400 KB, and 3000 to 6000
  allocations per frame. Drawing is bounded (visible rows only), but list
  building is not: it is O(ops) every frame with no caching and no windowing.
  Separately, if the user has pressed `o` or clicked "Show paint outlines",
  `drawDevOps` (`devtools_ops.go:23-42`) strokes an outline for every painted op
  through `vector.StrokeRect`, 1060 times per frame, with no cull against the
  window rect and no clip to the page area. Ops hidden under the dock or scrolled
  out of view still get stroked. Estimate 2 to 5 ms per frame on the reporter's
  machine.

Fullscreen: the dock width is a fixed 340 px (`devtools_dock.go:5`), clamped to
the window and floored at 220 (`devtools_dock.go:31-46`). At 1920 px wide it
covers 18 percent of the window, at 1000 px it covers 34 percent. The panel's own
draw cost does not scale with window width, but it does grow a little with height
through the visible row count. The page behind it is still replayed in full:
`Draw` paints the content first and the dock last (`draw.go:19-32`), and no
replay call is given a clip rect, so the strip under the dock is drawn and then
covered.

Practical consequence for the user's measurements: with the dock open on the Ops
tab, the Frame and Draw numbers include 0.5 to 3 ms of dock work, and with the
outlines on, several ms more. Those numbers should be read with the dock on the
Frame tab or with Perf on and the dock closed. The dump harness avoids this
problem entirely because it never imports `internal/window`.

## 3. Perf sampling

All of this only runs when the window opted in (`WindowOptions.Perf`,
`run_options.go:45`, or `WithPerf`).

- `devFrameTime` (`devtools_misc.go:11-18`) is called unconditionally at the top
  of every `Draw` (`draw.go:10`), even with Perf off and the dock closed: two
  `time.Now` and a subtraction. Constant, no allocation.
- `perfFrameSample` (`perf_stage.go:31-43`) is per frame. It records the frame
  into the ring (no allocation, `perf_ring.go:19-28`) and then calls `avg`,
  `p95`, `p99`, and `longFrames`. Each of those calls `copy()`
  (`perf_ring.go:32-39`), which allocates a new `[]time.Duration` of up to 120
  entries, and the two quantile calls also run `sort.Slice` over it. Measured on a
  copy of the exact code with a full ring: 8 allocations, 4208 bytes, and 2.09 us
  per frame. That is about 0.01 percent of a 16.7 ms frame and 240 KB per second
  of garbage, so it is not the reported problem, but it does show up in an
  `AllocsFrame` measurement and it is pure waste at 60 FPS. The two extra
  allocations per sort come from `reflect.Swapper` inside `sort.Slice`.
- Runtime sampling (`perf_runtime.go:26-44`) runs at most once per
  `perfSampleGap`, which is 500 ms, so twice a second. Each sample calls
  `runtime.ReadMemStats` (line 32) plus `perfRSS` (line 42), which reads
  `/proc/self/statm` and parses it with `strings.Fields` (lines 71-84, one heap
  allocation), and `runtime.NumGoroutine`. `ReadMemStats` is the expensive part,
  estimate 0.1 to 1 ms and a brief stop-the-world on some versions, twice a
  second. If the Frame tab is open it shows these cached numbers, so opening the
  dock does not add runtime sampling.
- With Perf on, `Update` also wraps the tick and sync stages in clock reads
  (`update.go:50`, `58`, `perf_stage.go:47-53`), which is 4 extra `time.Now`
  calls per frame. Negligible.

The board itself does not enable Perf (`main.go:61` calls `ownframe.Run`), so the
Frame and Draw rows in the panel come from `devFrameTime` and the `drawContent`
timer (`draw.go:19-25`), and the Frame avg/p95/p99 rows read `-`. To reproduce
the reported 60 ms frame and 23 ms draw while reading the p95 numbers, the board
needs `WindowOptions{Perf: true}` or `WithPerf(true)`.

## 4. One dirty rect per frame, and what a scattered tick does to it

The window calls `TakeDirty` exactly once per frame. The only two call sites are
`replay_partial.go:58` and `replay_viewport.go:30`, and the viewport one is used
only when `oversized(contentW, contentH)` (`replay_partial.go:52-55`), which is
mutually exclusive with the plan path. `TakeDirty` returns at most one
rectangle and clears the page state (`page_dirty.go:8-13`), and the page stores
exactly one rectangle (`p.dirty`, `page_types.go:62`). `markRect` unions into it
(`page_dirty_box.go:40-46`) and `image.Rectangle.Union` is the bounding box, so
scattered marks collapse into one rect per frame, never a list.

For a tick that invalidates scattered cells across all eight rows:

- Within one frame, every cell rect is unioned into one rectangle. Because cells
  exist in all eight rows and in every field from time to status, the bounding
  box spans the full board width and height. `TakeDirty` then insets it by
  `dirtyPad` = 4 px and intersects the content (`page_dirty.go:24-27`), which
  leaves a full-board rect.
- `planRepaint` (`replay_plan.go:32-52`) compares the clamped rect to the full
  content rect. Equal, or clamped away, or a size mismatch, means `repaintBuffer`
  (full replay into the buffer). Different means `repaintRect`, even if the rect
  covers 90 percent of the board. There is no middle ground and no multi-rect
  mode, so a rect that covers most of the board is still called a partial repaint.
- The union is per frame, not cumulative across frames: `TakeDirty` clears it, so
  a frame that marks nothing is a `repaintBlit` frame as long as the generation
  has not changed (`replay_plan.go:38-44`).

Consequences for two animation shapes, using the board's own flipper:

- Left-to-right flap ripple as currently written. `flipper.rebind` gives cell `i`
  in a row `delay = i % 8` and `spin = 8 + i % 6` (`board/flip.go:57`), and
  `step` decrements delay then spin (`flip.go:82-102`). The stagger is by cell
  index modulo 8, and cell index runs across all four fields in a row, so cells
  with `i % 8 == k` land in the time field, the destination, the platform, and
  the status. At every frame of the wave the active cells therefore span nearly
  the full row width, in all eight rows. The per-frame rect is the whole board,
  so each wave frame is a full replay (plus, on the buffer path, a buffer fill and
  a blit). There is no gain over today during the wave.
  The wave only lasts about 21 frames anyway, because cell `i` finishes at frame
  `(i % 8) + 8 + (i % 6)`, between 8 and 21. So the board is animated for roughly
  0.35 s out of every 12 s, and static the rest of the time except for the
  refresh bar.
- Row-band cascade. If only whole contiguous rows are active, the union is that
  band of rows full width. Two of eight rows is about 25 percent of the content
  area and roughly 25 percent of the ops after the `opTouches` filter
  (estimate 260 ops, about 6 ms at the reported per-op cost). That is a real win,
  but only while the band is narrow. Note that alternate rows, or a cascade that
  leaves one cell spinning in a far row, union back to the full height.
- A genuinely left-to-right wave front (delay as a function of column position
  across the whole board rather than cell index modulo 8) would give a narrow
  vertical band: the full height but only a few columns wide. That is the one
  ripple shape the single-rect design rewards, estimate 10 to 15 percent of ops
  per frame, so about 2 to 4 ms at the reported per-op cost.

## 5. Invalidate cost, and the per-frame allocation a tick should avoid

`Invalidate(id)` (`page_invalidate.go:10-18`) branches to `markFull` when the id
is empty or unknown, otherwise to `markPending` (lines 23-35). Per call that is:

- `hasBox` (line 11) then `markID` -> `hasBox` again (line 50). Each is a map
  lookup that falls back to a linear scan of every box when the id is missing
  (`page_boxcache.go:34-44`). For a real id it is two O(1) map hits. For a typo it
  is an O(boxes) scan and then a full-frame dirty, which is a silent performance
  cliff, not just a correctness one.
- `markElement` (lines 61-70) does the real work: `growBox` scans every box in the
  page and unions each one contained in the rect
  (`page_dirty_box.go:14-27`), then two `markRect` unions, then a map write to
  `p.last`. `growBox` is O(boxes) per call, estimate 300 to 400 boxes for this
  board, so 240 calls in one tick is about 80,000 to 100,000 loop iterations per
  frame, estimate 0.5 to 1.5 ms per frame.
- `markPending` allocates the pending map on first use each frame
  (`page_invalidate.go:30-34`). This is the per-frame allocation to avoid:
  `TakeDirty` sets `p.pending = nil` (`page_dirty.go:13`), which drops the map, so
  the next frame that invalidates anything allocates a fresh `map[string]bool`.
  The map exists so `applyPending` can union an element's new box after the next
  Redraw (`page_dirty.go:68-74`), which a tick that never redraws does not need.

`MarkRect` (`page_frame.go:7`) is the cheap path: one `markRect` union per call,
no map lookups, no `growBox`, no allocation. For a tick that already knows where
its cells are, which this flipper does through the bound `op` pointers and the
boxes, `MarkRect` per changed cell is the right call. `Invalidate` is the right
call when a handler changes an element's content and wants the layout's box for
it. A tick that redraws nothing should not use it.

Also note that `UseFrameDirty` and `FrameDirty` are a per-frame opt-in:
`FrameDirty` reads and clears the flag (`page_frame.go:15-20`), and the window
consumes it once per frame in `fullReplay()` (`replay_frame.go:17`). A tick that
sometimes changes nothing (paused, no flap, clock unchanged) should still call
`UseFrameDirty` unconditionally at the top, so the window stays on the buffer
path and the empty `TakeDirty` result becomes a `repaintBlit` frame.

## 6. Other per-frame work on this page

- `pointer()` runs every `Update` and calls `hoverCursor`, which calls
  `app.Hover` unconditionally (`internal/window/pointer.go:28`,
  `hover_cursor.go:6-9`). `Page.Hover` sets the coordinates and runs
  `boxIDAt`, a linear scan of every box (`internal/page/pointer_state.go:7-15`,
  `81-95`). `setHover` then early-returns when the id is unchanged
  (`pointer_state.go:62-65`), so the cost is the scan, not a redraw. That is an
  O(boxes) scan on every frame even when the mouse has not moved, estimate 10 to
  40 us at 300 to 400 boxes, and it is pure waste while idle.
- `keys()` runs every frame: 4 `IsKeyPressed` calls, a 3-key devtools watch
  (`devtools_keys.go:22-35`), and `ebiten.AppendInputChars` into a reused slice
  plus two `strings.ReplaceAll` calls on the result (`keys.go:33-36`). The
  ReplaceAll calls return the original string when there is no newline, so the
  usual frame costs no allocation.
- `pollReload` (`reload.go:17-46`) is gated to once per 250 ms and the board's
  page has no watched file (`Config.HTML`, not `Config.File`), so it returns
  after a type assert and a timer check. No per-frame disk work.
- `syncImage` -> `built()` (`sync.go:14-54`) returns early because the generation
  matches, so the page is not re-rendered per frame. It costs a generation read,
  a size read, and a canvas-size read. Constant.
- `prepareBitmapViewport` (`bitmap_viewport.go:19-27`) type-asserts a
  fallback-display interface and returns because the board is a display-list
  page, disposing nothing. Constant.
- `keyEvents` -> `s.chars = ebiten.AppendInputChars(s.chars[:0])` reuses the
  buffer. Fine.
- On the direct path (today's board), `drawText`
  (`internal/replay/text.go:15-37`) runs `layout.DisplayTransformText` and calls
  `textFace` per text op. `textFace` takes a global mutex and does two map
  lookups per call (`internal/replay/text_cache.go:32-70`, lock at line 37).
  With roughly 250 to 260 text ops per frame that is about 250 lock/unlock pairs
  and 500 map lookups per frame, estimate 10 to 40 us, plus the Ebiten
  `text.Draw` cost per op (it pulls glyph buffers from a sync.Pool, shapes the
  run, realizes glyph images from an atlas cache, and draws one quad; ebiten
  v2.10.4 `text/v2/layout.go:139` onward). The `h1` has `letter-spacing: 2px`
  (`board.html:21`), so `drawText` takes the per-glyph branch (lines 31-36) and
  does 10 `Draw` plus 10 `Measure` calls for that one heading.
- `flipper.step` (`board/flip.go:82-102`) iterates all cells every frame and
  skips the finished ones. That is O(cells), about 260, and it is cheap, but it
  is the source of the dirty information that F1 needs to produce.
- The refresh bar is rewritten every frame while unpaused (`tick.go:73-77`), so
  after F1 the steady state is one small wide rect per frame, not a blit frame.
  Quantizing the bar width (update it at 10 Hz or only on a change of 2 px) would
  turn most frames into zero-op blit frames.

## Ranked changes

Ranked by expected effect on this board's frame time. "App" means
`examples/departure-board`, "lib" means the library. Estimates are marked.

1. App: call `UseFrameDirty()` at the top of `Tick` every tick, and mark what
   changed with `MarkRect`, not `Invalidate` per cell. Mark the refresh bar rect,
   the clock glyph run when its text changes, and each flapping cell rect while it
   spins. Effect: steady state drops from 1060 replayed ops to 1 to 3 drawn ops
   plus the filter walks and the blit, estimate 23 ms to 0.3 to 0.8 ms, and the
   dump should classify every steady frame as `rect` or `blit`. Files:
   `board/tick.go`, `board/flip.go` (a small `board/dirty.go` for the rect
   unions). This is F1's job.
2. App: make the wave front a function of horizontal position, not of cell index
   modulo 8 (`flip.go:57`). A left-to-right front gives a narrow vertical dirty
   band each frame instead of a full-board bounding box, estimate 2 to 4 ms per
   wave frame instead of 23, and the animation still reads as a ripple. Files:
   `board/flip.go`. Alternative if the look must stay: a contiguous two-row band
   cascade, which cuts about 75 percent of the wave-frame ops, estimate 6 ms.
3. Lib: cache the dock's Ops rows and window the list. Build rows for the visible
   band plus a small overscan, and invalidate the cache on a generation change or
   an outline toggle, instead of rebuilding about 1060 rows with 2 to 3
   `Sprintf` calls and a rune-slice per text op every frame
   (`devtools_ops_lines.go:13-70`). Also cull `drawDevOps` to ops whose bounds
   meet the window rect (`devtools_ops.go:23-42`). Effect: removes an estimated
   0.5 to 3 ms per frame and 200 to 400 KB per frame with the dock open on the
   Ops tab, and several ms more with outlines on. This matters because the user
   reads the Frame numbers with the dock open, and the dock currently inflates
   them. Files: `internal/window/devtools_layout.go`,
   `devtools_ops_lines.go`, `devtools_ops.go`, `devtools_content.go`.
4. App: quantize the refresh bar so most frames mark nothing. Effect: the steady
   state becomes `repaintBlit`, which is the blit plus two filter walks, estimate
   0.2 to 0.4 ms. Files: `board/tick.go`.
5. Lib: skip `screen.Fill(pageBackground())` when the replay buffer or a
   full-canvas background op will cover the window, and cache the page background
   colour per generation so `pageBackground` stops boxing a `color.RGBA` into the
   `color.Color` interface (measured 1 allocation per call; it is called once per
   frame at `draw.go:13` and again at `replay_buffer.go:20` or `28`). Effect: one
   full-window fill removed, 1 to 3 small allocations removed per frame. Files:
   `internal/window/draw.go`, `background.go`, `replay_partial.go`,
   `replay_buffer.go`.
6. App: cut ops per tile. Each tile currently paints a background fill and a 1 px
   border (`board.html:55-71`), so about 250 of the 1060 ops are tile strokes
   (estimate). Dropping the border for one livery or moving it to a row-level
   fill removes roughly 25 percent of the list, which helps every full-buffer and
   wave frame. Files: `board/board.html`, `board/theme.go`.
7. Lib: skip `app.Hover` when the cursor position is unchanged for the frame, or
   cache the last `boxIDAt` result by point. Effect: removes an O(boxes) scan per
   frame, estimate 10 to 40 us. Files: `internal/window/pointer.go`,
   `hover_cursor.go`, or `internal/page/pointer_state.go`.
8. Lib: recompute the perf ring summary at most a few times a second instead of
   four ring copies, three sorts, and 8 allocations per frame (measured 4208
   bytes and 2.09 us per frame). The Frame tab can read the cached summary.
   Files: `internal/window/perf_stage.go`, `perf_ring.go`.
9. Lib: clip the page replay to the region left of the dock while the overlay is
   open, and cull offscreen ops on the direct path (`DrawVisiblePinned` already
   filters by bounds, but the buffer path draws the full content and the dock
   then covers 340 px). Effect: at 1920 px wide, about 18 percent less pixel work
   for the page replay with the dock open. Files: `internal/window/draw.go`,
   `replay_partial.go`, `devtools.go`.
10. Lib: let a tick batch element invalidations, so `Invalidate` does one
    `growBox` pass for a list of ids instead of one per id, and let the pending map
    survive `TakeDirty` when no Redraw is coming. Only needed if F1 chooses
    `Invalidate` over `MarkRect`. Files: `internal/page/page_invalidate.go`,
    `page_dirty.go`.

  build. The two measurements I did run are the `color.Color` boxing check and
  the perf ring check, both on copies outside the repo.
- The exact dock row heights and visible-row counts, which depend on the bitmap
